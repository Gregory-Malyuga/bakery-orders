# BUG-09 — production `/admin` отвечает 500 после релиза без миграции

**Статус:** открыт. **Приоритет:** P1. **Дата обнаружения:** 2026-11-01.

**Связанные задачи:** BAK-01, BAK-14.

## Наблюдение

- Пользователь открыл `https://xn----8sbfmclbpnvckotr1m.xn--p1ai/admin` под администратором и получил HTTP 500. На экране отображается `Server Error`.
- На `backery` PHP и PostgreSQL-контейнеры healthy, HTTPS `/health` отвечает 200. Перезапуск Caddy не устраняет ошибку схемы БД.
- Отчёт из журнала Laravel без передачи сырых строк: 21 запись `production.ERROR`, SQLSTATE `42703` (неизвестный столбец). `php artisan migrate:status` показывает `2026_11_01_120000_add_bakery_return_cancellations` как `Pending`.
- Влияние: административная страница заказов недоступна; рабочие данные и том PostgreSQL не менялись при диагностике.

## Причина

Релиз запустил новый PHP-код, но `scripts/deploy-production.py` не запускал миграции. `OrderReturnSummary::forOrders()` фильтрует `bakery_returns.status`, который добавляет ожидающая миграция. Наличие PostgreSQL-тома проверялось, но схема оставалась прежней.

Предупреждения встроенного Caddy в PHP-контейнере о `/data` и `/config` относятся к правам каталогов и не объясняют SQLSTATE `42703`.

## Исправление и приёмка

- После запуска Compose и проверки прежнего PostgreSQL-тома выполнять `php artisan migrate --force --no-interaction` в новом PHP-контейнере. Ошибка миграции должна прерывать релиз до проверки `/health` и очистки образов.
- Передавать deploy-скрипт и Compose/Caddyfile из checkout GitHub Actions в каталог релиза по SHA; на сервере не должно быть отдельной вручную установленной исполняемой копии.
- После релиза проверить статус миграции `Ran`, HTTPS `/health` и авторизованный `/admin` (200), сохранность существующего тома БД и повторный релиз без повторного применения миграции.
- До подтверждения этих проверок дефект остаётся открытым.
