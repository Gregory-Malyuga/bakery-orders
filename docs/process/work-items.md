# Работа с задачами и ошибками

Это рабочий процесс для сервиса пекарни. Он адаптирован по структуре документации OEM: **roadmap → проверка → исправление → итог в state**, с отдельной историей разобранных сбоев. Подробные требования к текущим задачам находятся в [бэклоге](../backlog-2026-11-01.md). Этот процесс не меняет функциональность приложения и не означает, что задача уже выполнена.

## Где что хранится

| Документ | Назначение |
| --- | --- |
| [roadmap.md](roadmap.md) | Очередь задач и открытых ошибок: ID, приоритет, краткая формулировка, чекбокс завершения. Это точка входа. |
| [backlog-2026-11-01.md](../backlog-2026-11-01.md) | Подробная постановка BAK-01…BAK-12: поведение, критерии приёмки, зависимости и нерешённые вопросы. |
| [state.md](../state.md) | Короткий снимок: что сейчас в работе, что дальше, что мешает, какие проверки прошли. Не заменяет roadmap. |
| [history/index.md](../history/index.md) и [checklist.md](../history/checklist.md) | Разобранные неожиданные сбои и повторяемые диагностические признаки. Не очередь открытых багов. |
| [ADR](../adr/index.md) | Утверждённые решения с альтернативами и последствиями, если выбор влияет на дальнейшую архитектуру или бизнес-правило. |

## Как завести задачу или баг

1. Проверить roadmap и подробный бэклог на дубликат. Если обнаружена новая ошибка, записать **фактический симптом**, шаги воспроизведения, ожидаемое и фактическое поведение, влияние на деньги/заказы/документы и источник наблюдения. Не объявлять гипотезу подтверждённой причиной.
2. Дать постоянный ID: `BAK-XX` для задачи из текущего бэклога, `BUG-XX` для новой ошибки. Следующий номер брать из roadmap; существующие ID не переиспользовать. Для внешнего трекера сохранять ссылку рядом с локальным ID, если задача там создана; Markdown-запись не выдавать за внешний issue.
3. Назначить приоритет: **P0** — искажённые рабочие деньги/данные или невозможность исправить ошибку текущего дня; **P1** — важный ежедневный документ или расчёт; **P2** — запланированное развитие; **P3** — улучшение без срочного операционного эффекта. Приоритет может пересматриваться при новых фактах.
4. Добавить в roadmap строку `[ ]` со ссылкой на подробную постановку. Для бага краткая постановка может быть прямо в roadmap; если она разрастается, создать `docs/process/bugs/BUG-XX.md` по [шаблону бага](bug-template.md) и оставить ссылку. В постановке нужны критерии приёмки и зависимости.
5. Если неизвестны формула, данные или правило бизнеса, явно записать вопрос и отдельно указать, какие части можно делать до ответа. Не придумывать правило ради закрытия задачи.

## Как выполнять

1. Открыть [state.md](../state.md), затем текущий раздел [roadmap.md](roadmap.md), потом постановку выбранного ID. Проверить Git-состояние и сохранить чужие локальные изменения.
2. Для бага воспроизвести симптом на безопасных данных и установить причину по коду, тесту, журналу или текущему состоянию. Для задачи проверить существующее поведение и все затронутые поверхности: кабинет магазина, админку, печать, Excel и отчёты — по применимости.
3. Зафиксировать в `state.md` текущий ID, результат диагностики и реальные блокеры. Для изменения поведения добавить тесты на значимые правила и пограничные случаи; для небольшого изменения текста достаточно проверки результата и ссылок.
4. Реализовать минимальный согласованный объём. Для данных и финансов проверить сохранение истории, права доступа, повторную отправку и миграции. Не исправлять соседние несвязанные задачи одним коммитом без явной связи.
5. Пройти релевантные проверки; для изменения приложения затем выполнить полный `composer pre-push`, когда окружение доступно. Для правки только документации проверить ссылки и diff. Записать **что реально запускалось** и результат; недоступный PHP/Docker или непроверенный браузер/печать не обозначать как прошедшие. Проверить видимый результат на всех затронутых страницах и выгрузках.
6. Только после выполнения критериев приёмки отметить `[x]` в roadmap, обновить `state.md` и при необходимости подробную постановку. Локальный коммит, push, CI и production-деплой — разные этапы; статус каждого указывать отдельно.

## Если возникла ошибка во время работы

- Сначала сверить симптом с [checklist.md](../history/checklist.md). Это подсказка для диагностики, а не доказательство причины.
- Если это **новый дефект продукта, который остаётся открытым**, завести `BUG-XX` в roadmap с воспроизведением и влиянием. Отдельно пометить, блокирует ли он текущую задачу.
- Если это **неожиданный сбой, причина и исправление которого уже установлены**, записать `HIST-NNN` по [шаблону истории](../history/index.md) и добавить диагностический признак в checklist. Ссылку на связанную задачу/баг указать в записи.
- Если причина пока неизвестна, сохранить в `state.md` факты, гипотезы и следующий способ проверки. Не записывать предположение в history как установленную причину и не закрывать bug.

## Формат короткого итога задачи

Указать ID и статус, что изменилось, как проверено (включая числа/файлы при наличии), что осталось, локальный commit SHA, состояние push/CI/deploy. Для финансовых задач отдельно подтвердить согласованность страницы, печати и Excel. Если задача остановлена из-за отсутствующего решения, назвать конкретный вопрос и уже выполненную независимую часть.
