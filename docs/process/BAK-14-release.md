# BAK-14 — ручной production release с резервной копией PostgreSQL

**Статус:** пайплайн изменён; первый реальный ручной запуск требуется проверить отдельно.

## Как выпускаем версию

1. Merge в `main` запускает CI/CD: тесты, анализ, build, security image scan и smoke.
   Автоматического production-деплоя **нет**.
2. После успешного CI откройте GitHub → Actions → **Deploy Production (manual)** → **Run workflow**.
   Выберите **main**, затем запустите workflow. Релиз берёт SHA актуального `main`.
3. `verify-release` требует существования успешного CI push-run с тем же SHA. Если
   образ ещё собирается или тесты не прошли, деплой блокируется.
4. Job `deploy-production` использует GitHub Environment `production` и получает
   секреты, не сохраняя `.env` на сервере.
5. Через SSH на хосте `bakery-deploy` сначала создаётся **обязательный бэкап** PostgreSQL;
   только после его проверки разрешаются `docker pull`, смена PHP-образа,
   `docker compose up --wait`, миграции и проверка `/health`.

**GitHub Environment:** можно включить required reviewers для второго
подтверждения перед выполнением job. Запуск manual workflow сам по себе
является ручным действием, но не заменяет проверку кода и резервной копии.

## Бэкап перед каждым релизом

Бэкап создаётся на файловой системе **сервера**, вне контейнера и Docker volumes:

```text
/home/bakery-deploy/backups/bakery-postgres/
  bakery-YYYYMMDDTHHMMSSZ-<12-символьный-SHA>.dump
```

- Архив создаётся `pg_dump --format=custom --no-owner --no-acl` из запущенного
  PostgreSQL-контейнера `laravel-app-postgres-1`.
- Бинарный поток `pg_dump` сразу пишется в файл на хосте, а не в контейнер и
  не в папку docker volume.
- Права каталога `0700`, файла `0600`; архив сначала пишется во временный
  `.partial`, затем выполняется `pg_restore --list` и атомарное переименование.
- Дополнительно проверяется, что PostgreSQL использует прежний
  `laravel-app_postgres_data`.
- Ошибка бэкапа, пустой архив, ошибка `pg_restore --list` или недостаток места
  **прерывают релиз до изменения Docker-образа или контейнеров**.
- Бэкапы не удаляются автоматически. Настройте контроль свободного места,
  ротацию и копирование в независимое хранилище.

**Важно:** архив на том же физическом сервере защищает от ошибок деплоя,
но **не** от потери самого сервера. Нужен отдельный off-host/off-site бэкап.
Успешный `pg_restore --list` подтверждает читаемость оглавления, но не
заменяет регулярный тест восстановления всей базы в отдельный PostgreSQL.

## Действия после создания копии

Release script `scripts/deploy-production.py`:

1. Запрашивает образы из GHCR строго по SHA и проверяет OCI revision.
2. Назначает рабочий тег `laravel-app-php:latest`.
3. Выполняет `docker compose up -d --no-build --wait --wait-timeout 120`.
4. Проверяет постоянный Docker volume PostgreSQL.
5. Запускает `php artisan migrate --force --no-interaction`.
6. Проверяет `https://<production-domain>/health`.
7. Оставляет старый image ID доступным для ручного rollback.

**Откат:** автоматического rollback и восстановления БД пока нет.
Изменения схемы, сделанные миграциями, могут потребовать восстановления из
резервной копии. До релиза запишите старый image ID и не удаляйте его.

Хост не нуждается в Git checkout и `.env`: source файлов деплоя передаётся
из текущего коммита через SSH stdin и хранится в
`/home/bakery-deploy/releases/<SHA>/`. PostgreSQL и Caddy volumes являются
`external: true`, отсутствие существующего тома блокирует деплой.
Использование `docker compose down -v` запрещено.

## Контрольный список

- [ ] CI для `main` полностью зелёный, включая production image build.
- [ ] Бэкап вне контейнера создан и путь с размером выведен в лог.
- [ ] Сделана независимая копия бэкапа вне сервера.
- [ ] Проверены `/health`, вход, оформление заказа, цены, печать и возвраты.
- [ ] Записан старый image ID и подготовлен ручной план отката.
- [ ] Выполнено тестовое восстановление в отдельную БД.

## Первичное развёртывание

Релиз рассчитан на **существующий production PostgreSQL и его volume**.
Первый запуск пустого сервера требует отдельной инициализации и не должен
обходить обязательное создание резервной копии существующей базы.
