# Стратегия тестирования bakery-orders

## Цель

Не допускать повторного появления дефектов, которые уже исправлялись. Полное покрытие строк **не гарантирует** правильность бизнес-правил. Критерий готовности: для каждого критичного требования имеются независимые тестовые сценарии (в том числе отрицательные), которые проверяют **результат**, а не внутренние методы.

## Установленная регрессия — колонки возвратов

При формировании сводной накладной в разных секциях использовались разные условия:
- Верхняя таблица: `show_return_columns && returned_quantity > 0`.
- Нижняя таблица состава группы: только `show_return_columns`.

Это позволяло показывать «Возврат, ₽» без фактических возвратов. Новые тесты `GroupInvoiceRegressionTest` проверяют HTML и содержимое реального XLSX, используя заказы и возвраты в БД:

1. Обычная группа без возвратов: нигде нет колонок возврата.
2. Обычная группа с возвратом: соответствующие колонки есть, итог после возврата верен.
3. Балтийская и Колпино с возвратом: колонки скрыты, финансовая сумма всё равно чистая.
4. Отменённый возврат: финансовая сумма восстановлена, колонки исчезли.

Важно: тесты выполняют генератор XLSX, а не проверяют только подготовленный массив. При любом изменении разметки или экспорта эти проверки должны оставаться обязательными.

## Матрица критичных тестов

| Подсистема | Позитивные проверки | Негативные/граничные проверки |
| --- | --- | --- |
| Авторизация/изоляция | Магазин видит только собственные цены и заказы | Другой магазин, незалогиненный пользователь, заблокированный аккаунт |
| Заказы | Оформление, идемпотентный повтор, отмена | Дедлайн 18:30, закрытые даты, старый quote hash, неверное количество |
| Прайсы/скидки | Индивидуальные цены, общий прайс, 10% скидка | Пустое поле, 0/100%, округление до копейки, изменение после заказа |
| Возвраты | Полный/частичный возврат, пересчёт суммы | Дубли, отменённый возврат, возврат после изменения цены |
| Документы | HTML, печать и XLSX совпадают с заказом | Отсутствующий возврат, отменённый возврат, группа без заказов |
| Группы | Несколько участников и общий итог | Участник в нескольких группах, скрытые возвраты, пустая группа |
| Производство/этикетки | Количество изделий и пакетов | Исключённые группы, разные виды фасовки, отменённые заказы |
| Склад/рецепты | Остатки, списания, расчёт потребности | Повтор, инвентаризация, отмена движения, ошибка единиц измерения |
| Аналитика/CSV | Итоги по датам/точкам/товарам | Пустой период, возвраты, отсутствующие заказы, разная таймзона |
| Сессии/деплой | Авторизация остаётся после перезапуска | Истекшая сессия, rollback, обязательные миграции |

## Требования к новым PR

1. Любое исправление production-багa включает тест, который падает на старом коде и проходит после исправления. Для UX-дефектов желательно также скриншотное/браузерное сравнение.
2. Тестировать не только сервис, но и API/контроллер, HTML, XLSX/CSV, финансы и права, если изменение их затрагивает.
3. На денежные правила: использовать целые копейки и проверять округления, нулевые/максимальные значения, сохранение истории.
4. Тесты должны быть детерминированными: фиксировать время, создавать изолированные данные, не полагаться на состояние production.
5. Перед merge требовать `PHPStan`, `Pint`, `Deptrac`, весь PHPUnit/ParaTest, миграции с PostgreSQL, а для изменений интерфейса — ручную или браузерную проверку.
6. Добавлять тестовый сценарий в эту матрицу при обнаружении нового типа регрессии.

## План достижения широкого покрытия

**Этап 1 — финансовая корректность и документы.** Проверить сквозную согласованность заказа, возврата, скидки, HTML и всех XLSX. Установить обязательные тесты для всех комбинаций «возвратов нет / активные / отменённые / дополнительные», обычных групп и специальных групп.

**Этап 2 — измерить фактическое покрытие.** Подключить coverage-драйвер (`PCOV` или `Xdebug`) в CI и публиковать HTML/Cløver отчёт как артефакт. Измерить стартовые значения отдельно для `Application`, `Infrastructure` и `Presentation`. Не объявлять процент без измерения. Ввести пороги постепенно: сначала запрет снижения покрытия и проверка изменённых строк, затем повышать пороги по модулям. Миграции, Blade и конфигурация требуют особых сценариев и не полностью отражаются в line coverage.

**Этап 3 — все основные бизнес-модули.** Дополнить проверки складских движений, рецептур, групп, календаря, исключений этикеток, аккаунтов, отчётов, конкурирующих заказов.

**Этап 4 — UI и production.** Автоматизировать E2E для входа, заказа, админских фильтров, форм, печати и прав; отдельно — smoke-тесты релиза с реальным PostgreSQL и HTTP.

**Этап 5 — усиление.** Mutation testing для критичных денежных формул, property-based сценарии для округления и сумм, регулярная проверка восстановления из бэкапа.

## Что проверено

В PR с этим документом код и тесты добавлены в GitHub. **Локальный запуск PHP/Composer, PostgreSQL, браузерных тестов и измерение покрытия не выполнены.** Числа покрытия не заявляются. До прохождения CI регрессионные тесты считаются непроверенными.
